UT1 · Teoría de procesos

Programa, proceso, hilo y servicio

TeoríaUT1.1

ConceptoDefinición corta
ProgramaConjunto de instrucciones guardado en disco. Es algo estático.
EjecutableFichero con el programa ya compilado/listo para que el SO lo cargue (.exe, binario, .class + JVM).
ProcesoPrograma en ejecución. Tiene su propia memoria, PID, estado y recursos asignados por el SO.
Hilo (thread)Secuencia de ejecución dentro de un proceso. Comparte la memoria del proceso. No puede existir solo.
ServicioProceso que se ejecuta en segundo plano, sin interfaz, normalmente al arrancar el sistema (demonio en Linux).

Un proceso está compuesto por

  • Las instrucciones que se van a ejecutar.
  • El estado del propio proceso.
  • El estado de ejecución (registros del procesador).
  • El estado de la memoria.

El SO necesita saber de cada proceso: PID (identificador único), estado actual, prioridad y ubicación en memoria.

Hilos vs procesos

Proceso

  • Memoria propia (imagen de memoria).
  • Crear y cambiar de proceso es costoso.
  • Se comunican con flujos, ficheros, sockets.
  • Si uno falla, los demás siguen.

Hilo

  • Comparte código, datos y ficheros del proceso.
  • Es ligero: menos recursos y conmutación rápida.
  • Se comunican por memoria compartida (variables, objetos).
  • Propio: id, contador de programa, registros y pila.
Ejemplo de examen: Word con un hilo revisando la ortografía mientras otro guarda automáticamente. Es un proceso con varios hilos.

Estados de un proceso y cambio de contexto

TeoríaUT1.2

EstadoQué significa
NuevoRecién creado.
Listo (ready)Esperando a que le den la CPU.
En ejecución (run)Usando la CPU ahora mismo.
Bloqueado (wait)Esperando un evento externo (E/S, señal...).
SuspendidoLlevado a memoria virtual / swap para liberar RAM.
TerminadoHa acabado y ya no necesita la CPU.

Contexto y PCB

  • Contexto: toda la información que define el estado de un proceso en un instante (estado del proceso, del procesador y de la memoria).
  • Cambio de contexto: sacar un proceso de la CPU guardando su contexto y cargar el de otro. Es tiempo perdido: la CPU no hace trabajo útil mientras.
  • El contexto se guarda en el PCB (Bloque de Control de Proceso).
  • Registros clave: contador de programa (siguiente instrucción) y puntero a pila.

Planificación

El planificador (scheduler) reparte la CPU entre procesos. Debe ser imparcial y eficiente, minimizar el tiempo de respuesta, ejecutar el máximo de procesos y equilibrar recursos. El SO organiza los procesos en colas:

  • Cola de procesos: todos los del sistema.
  • Cola de preparados: los listos para ejecutarse.
  • Colas de dispositivo: los que esperan una E/S.

Apropiativo (expulsivo)

  • El SO puede expulsar al proceso de la CPU.
  • Más coste, mejor uso de la CPU.
  • Sistemas multiusuario y multitarea.

No apropiativo

  • El proceso usa la CPU hasta que termina o se bloquea.
  • Sencillo, menor rendimiento.
  • Sistemas batch o monousuario.

El kernel es la parte del SO que gestiona los recursos; se accede a él mediante llamadas al sistema.

Multitarea, concurrencia, paralelismo y sistemas distribuidos

TeoríaUT1.1 · UT1.2

SecuencialUna línea de control. Orden estricto. El tiempo de cada operación no afecta al resultado.
ConcurrenteVarias líneas de control. Orden parcial. Dos procesos son concurrentes si la primera instrucción de uno se ejecuta entre la primera y la última del otro. Puede ser con 1 CPU (intercalando).

A la secuencialización entre procesos concurrentes se le llama sincronización.

Características de un sistema distribuido

  • Concurrencia de programas.
  • Sin reloj global: se sincronizan con mensajes.
  • Fallos independientes: un componente puede fallar sin tirar el resto.

¿Para qué usar concurrencia?

  • Optimizar recursos: la CPU está menos ociosa mientras hay E/S.
  • Interactividad con el usuario.
  • Disponibilidad: un servidor puede atender a varios clientes a la vez.
  • Diseño más modular y mantenible.

Tres tipos de interacción

  • Sincronización: un proceso conoce el punto de ejecución de otro.
  • Exclusión mutua: solo uno accede al recurso.
  • Sincronización condicional: solo se accede si el recurso está en cierto estado.

Formas de comunicarse

Intercambio de mensajes

  • Primitivas send / receive.
  • Por buffer de memoria (misma máquina) o socket (por red).
  • En Java se usan como streams: read / write.

Recursos compartidos

  • Primitivas write / read sobre el recurso.
  • Ficheros, memoria compartida, BD.

Labores del SO con la concurrencia

  • Seguir a los procesos activos.
  • Asignar y retirar recursos: CPU, memoria, archivos y E/S.
  • Proteger datos y recursos de cada proceso.
  • Que el resultado no dependa de la velocidad de los demás procesos.

Semáforos, monitores y paso de mensajes

TeoríaUT1.5

Semáforos

  • Tipo de dato con un valor y una lista de procesos suspendidos esperando.
  • Binario: solo 0 o 1. General: cualquier natural.
  • Valor 0 = cerrado; valor > 0 = abierto.
  • Analogía: baño con 3 cabinas. Entrar resta 1, salir suma 1; si vale 0, se espera.
  • Ventajas: fáciles de entender y resuelven cualquier problema de concurrencia.
  • Inconvenientes: bajo nivel, un olvido o cambio de orden provoca interbloqueos, y la lógica queda repartida por todo el código.
  • Java: java.util.concurrent.Semaphore (para hilos de un mismo proceso).
Semaphore sem = new Semaphore(3);   // 3 permisos (3 cabinas libres)

sem.acquire();          // resta 1; si es 0, el hilo espera
try {
    // región crítica
} finally {
    sem.release();      // suma 1 y despierta a uno que esperaba
}

Monitores

  • Encierran los recursos compartidos como componentes privados y garantizan acceso en exclusión mutua.
  • Incluyen: variables privadas, procedimientos públicos (la interfaz), un cuerpo que inicializa y una cola de procesos suspendidos.
  • Ventajas: uniformidad, modularidad, simplicidad y eficiencia.
  • Desventaja: con muchas condiciones de sincronización el código se complica mucho.
  • En Java: cualquier objeto con métodos synchronized (+ wait/notify).

Paso de mensajes

No necesita memoria compartida. Intervienen el emisor, el receptor y el mensaje.

Asíncrono

  • El emisor no espera a que se reciba.
  • Usa buzones o colas.
  • Solo se bloquea si el buzón está lleno.

Síncrono (rendezvous)

  • El emisor espera a que el receptor lo reciba.
  • Incluye la llamada a procedimiento remoto (RPC), típica de cliente/servidor.

Lectores-escritores con ficheros

  • Solo lectura: el SO deja leer a todos los lectores a la vez.
  • Escritura: acceso exclusivo. El escritor espera a que acaben los lectores, y los demás esperan al escritor.

UT1 · Procesos en Java

ProcessBuilder y Process

TeoríaUT1.3 · UT1.4

Las dos clases están en java.lang (no hace falta importarlas). ProcessBuilder configura el proceso (comando, directorio, entorno, redirecciones) y start() lo lanza devolviendo un Process, que sirve para controlarlo.

new ProcessBuilder(List<String> comando);      // comando + argumentos en una lista
new ProcessBuilder(String... comando);         // varargs: "java", "-cp", cp, "Clase", "arg"

Métodos de ProcessBuilder

MétodoQué hace

redirectOutput(File)La salida del hijo va a un fichero.
redirectError(File)Los errores del hijo van a un fichero.

Métodos de Process

Ojo con los nombres: parecen al revés. getInputStream() es la salida del hijo (entrada para el padre) y getOutputStream() es la entrada del hijo.
Procesos especiales: los métodos de Process no funcionan bien sobre servicios, shell scripts o demonios del SO.

Operaciones básicas (teoría)

  • Creación: padre e hijo se ejecutan concurrentemente; cada uno con su memoria (imagen de memoria). El padre puede esperar con wait (waitFor()).
  • Terminación: el hijo avisa al SO con exit (System.exit(n)) y así manda información al padre.
  • Un hijo puede crear más procesos: se forma un árbol de procesos.

Runtime, directorio de trabajo y entorno

TeoríaUT1.3 · ejemplos 1–4

ProcessBuilder

  • Primero se configura todo (comando, directorio, entorno) y luego start().
  • Forma recomendada.

Runtime

  • El proceso se crea "en vacío" y el comando se pasa en exec(...).
  • exec(String) está deprecado desde Java 18: usa exec(String[]).

Ambos devuelven un objeto Process. Los recursos del hijo los libera el SO al hacer exit; los objetos Java los limpia el garbage collector.

import java.io.IOException;

public class EjecutarAplicacionProcessBuilder {

    public static void main(String[] args) {
        // Comando + argumentos, cada uno en un String separado (varargs)
        // Windows: "notepad.exe"   ·   Linux: "gedit"   ·   macOS: "open", "-a", "TextEdit"
        ProcessBuilder pb = new ProcessBuilder("notepad.exe");
        try {
            Process p = pb.start();          // crea el proceso hijo
            System.out.println("Proceso lanzado. PID: " + p.pid());
            int codigo = p.waitFor();        // el padre espera a que cierres el bloc de notas
            System.out.println("El hijo terminó con código " + codigo);
        } catch (IOException e) {
            System.out.println("No se encontró el programa: " + e.getMessage());
        } catch (InterruptedException e) {
            e.printStackTrace();
        }
    }
}
import java.io.IOException;

public class EjecutarAplicacionRuntime {

    public static void main(String[] args) {
        // Runtime: el proceso se crea "en vacío" y el comando se pasa al ejecutar
        Runtime rt = Runtime.getRuntime();
        try {
            // exec(String[]) evita el exec(String) deprecado desde Java 18
            Process p = rt.exec(new String[] {"notepad.exe"});
            p.waitFor();
            System.out.println("Fin. Código: " + p.exitValue());
        } catch (IOException | InterruptedException e) {
            e.printStackTrace();
        }
    }
}
import java.io.IOException;

public class DestruccionProceso {

Comunicación padre ↔ hijo

TeoríaFlujos estándar

● Argumentos: al arrancar ● Entrada: mientras se ejecuta ● Salida: lo que imprime el hijo ● Exit: al terminar
CanalDirecciónCuándoCómo
Argumentospadre → hijoAl arrancarEn el ProcessBuilder; el hijo los lee en args[].
Entradapadre → hijoDurante la ejecuciónPadre escribe en getOutputStream() o redirectInput; hijo lee System.in.
Salidahijo → padreDurante la ejecuciónHijo println; padre lee getInputStream() o redirectOutput.

Orden correcto

  1. Escribir en la entrada del hijo y cerrarla (bw.close()). Si no se cierra, el hijo espera más líneas para siempre.
  2. Leer toda la salida del hijo hasta que readLine() devuelva null.
  3. Llamar a waitFor(). Si se hace antes de leer y el hijo escribe mucho, el buffer se llena y los dos se bloquean (deadlock).
// Enviar al hijo: imprescindible el salto de línea
respuesta = respuesta + "\n";
OutputStream os = p.getOutputStream();
os.write(respuesta.getBytes());
os.flush();                       // vacía el buffer
os.close();

// Recoger la salida
int exitVal = p.waitFor();
System.out.println("Valor de Salida: " + exitVal);
if (exitVal == 0) {
    InputStream is = p.getInputStream();
    Scanner sc2 = new Scanner(is);
    while (sc2.hasNextLine()) {
        System.out.println(sc2.nextLine());
    }
    is.close();
}

Redirigir entrada y salida a ficheros

TeoríaUT1.5

Para guardar la salida de un proceso en un log o leer su entrada de un fichero no hace falta tocar el hijo: se configura en el ProcessBuilder antes de start().

ProcessBuilder pb = new ProcessBuilder("java", "-cp", cp, "Hijo");

pb.redirectInput(new File("entrada.txt"));    // System.in  del hijo <- fichero
pb.redirectOutput(new File("salida.txt"));    // System.out del hijo -> fichero (sobrescribe)
pb.redirectError(new File("error.txt"));      // System.err del hijo -> fichero

// Añadir al final en vez de sobrescribir
pb.redirectOutput(ProcessBuilder.Redirect.appendTo(new File("log.txt")));

// Usar la consola del padre
pb.redirectOutput(ProcessBuilder.Redirect.INHERIT);   // o pb.inheritIO() para los tres

Process p = pb.start();
int codigo = p.waitFor();
Al redirigir, el stream queda vacío: si haces redirectInput, p.getOutputStream() devuelve un NullOutputStream. Si haces redirectOutput, p.getInputStream() no da nada.
¿Dónde se crean los ficheros? En el directorio de trabajo: en Eclipse, la carpeta del proyecto (no src ni bin). Si quieres otra carpeta, pon la ruta al crear el File.

Sincronizar procesos con ficheros (File y FileLock)

TeoríaUT1.6 · procesos competitivos

Java no tiene palabras reservadas para sincronizar procesos (para hilos sí: synchronized). Se usan recursos externos: ficheros como semáforo, FileLock de Java NIO, pipes, sockets o una BD.

¿Por qué sincronizar?

  • Compartir recursos sin conflictos: que dos procesos no escriban a la vez en el mismo archivo.
  • Mantener el orden: B depende de A (A descarga un fichero, B lo procesa).
  • Evitar condiciones de carrera.

El SO garantiza que cada write individual es atómico, pero dos operaciones separadas pueden intercalarse: A escribe AAAAA y B escribe BBBBB, y sale ABBAABBABA.

Tres formas

FormaCómoProblema
lock.exists() + createNewFile()Comprobar si existe y luego crearloIncorrecto: dos procesos pueden pasar el exists() a la vez.
while (!lock.createNewFile())createNewFile es atómico: devuelve false si ya existeFunciona, pero con espera activa (sleep entre intentos).
FileChannel.lock()Bloqueo real del SORecomendada. El proceso se bloquea sin consumir CPU.
File lock = new File("lock.tmp");
while (lock.exists()) {        // ¡dos procesos pueden pasar aquí a la vez!
    Thread.sleep(100);
}
lock.createNewFile();          // "adquirir"
// usar el recurso
lock.delete();                 // liberar
File lock = new File("lock.tmp");
while (!lock.createNewFile()) {   // atómico: false si ya existe
    Thread.sleep(100);
}
try {
    // usar el recurso
} finally {
    lock.delete();                // liberar SIEMPRE
}
File lockFile = new File("lock.tmp");
lockFile.createNewFile();
try (FileOutputStream fos = new FileOutputStream(lockFile);
     FileChannel channel = fos.getChannel();
     FileLock lock = channel.lock()) {      // se bloquea si otro proceso lo tiene
    // región crítica
} finally {
    if (lockFile.exists()) lockFile.delete();
}
// FileLock es AutoCloseable: al salir del try se libera solo
Usa un fichero SOLO para el bloqueo (datos.lock) y otro para los datos (datos.txt). Si bloqueas y escribes con el mismo objeto, o usas PrintWriter/BufferedWriter sobre él, no se sincroniza bien.
Dentro de la MISMA JVM no se puede pedir dos veces el lock del mismo fichero: lanza OverlappingFileLockException. FileLock es para procesos distintos.

Ejemplo completo: dos procesos escribiendo letras

import java.io.FileWriter;
import java.io.IOException;

// Ejemplo 1: dos procesos escriben en el MISMO fichero sin sincronizar.
// Uso: java EscribeLetrasSinBloqueo A
public class EscribeLetrasSinBloqueo {

    public static void main(String[] args) throws IOException, InterruptedException {
        String letra = args.length > 0 ? args[0] : "A";

import java.text.Normalizer;

public class Ejercicio3 {

    public static void main(String[] args) {
        if (args.length == 0) {
            System.exit(-1); // sin texto -> error
        }

        // Une todos los argumentos por si la frase llega partida en varios
        // (pasaría desde terminal sin comillas: java Ejercicio3 Ana lava lana)
        String texto = String.join("", args);

        // Limpieza en 3 pasos:
        // 1. toLowerCase()          -> todo a minúsculas
        // 2. Normalize NFD + \p{M}  -> separa la letra de su tilde y borra la tilde
        // 3. [^a-z0-9ñ]             -> borra lo que no sea letra o número
        texto = Normalizer.normalize(texto.toLowerCase(), Normalizer.Form.NFD)
                .replaceAll("\\p{M}", "")
                .replaceAll("[^a-z0-9ñ]", "");

        // Da la vuelta al texto
        String invertido = new StringBuilder(texto).reverse().toString();

        // Es palíndromo si no está vacío y es igual al revés
        if (!texto.isEmpty() && texto.equals(invertido)) {
            System.out.println("Es palíndromo");
        } else {
            System.out.println("NO es palíndromo");
        }
        System.exit(0);
    }

UT2 · Teoría de hilos

Concepto de hilo

TeoríaUT2.1

Un hilo (thread o subproceso) es la unidad básica de uso de la CPU: una secuencia de código en ejecución dentro del contexto de un proceso. Tiene identificador único. Todo programa tiene al menos el hilo principal (el del main).

Características

CaracterísticaExplicación
Dependencia del procesoNo se ejecutan solos; siempre dentro de un proceso.
LigerezaNo crean procesos nuevos: se pueden crear muchos con poco coste.
Compartición de recursosComparten la memoria del proceso → posibles colisiones (errores de concurrencia).
ParalelismoAprovechan los núcleos del procesador.
ConcurrenciaAtienden muchas peticiones a la vez (servidores web, BD).

Comparten entre ellos

  • Sección de código y de datos.
  • Variables globales / static.
  • Recursos del sistema (ficheros).

Cada hilo tiene

  • Identificador único.
  • Contador de programa.
  • Registros de la CPU.
  • Pila de variables (locales).

Beneficios

  • Capacidad de respuesta: el programa sigue atendiendo aunque una tarea sea larga.
  • Compartición de recursos sin reservar memoria extra.
  • Paralelismo real en multinúcleo.
  • Prioridades para tareas críticas.
  • Menor tiempo de creación, terminación y conmutación que un proceso.

Fases de un programa multihilo

  1. Descomposición funcional: identificar tareas y sus relaciones.
  2. Partición: los hilos se comunican por memoria (rápido, pero ojo a la sincronización).
  3. Implementación: Thread o Runnable + mecanismos de sincronización.

Hilos de usuario vs hilos de kernel

Nivel de usuario

  • Los gestiona una librería; el SO solo ve un hilo.
  • Cambio de contexto más sencillo.
  • Funcionan aunque el SO no tenga hilos.
  • Planificación propia.

Nivel de kernel

  • El SO los crea, planifica y gestiona.
  • Aprovechan multiprocesador.
  • Si uno se bloquea, los demás siguen.
ModeloRelaciónPros / contras
M×1 (many to one)Muchos hilos de usuario → 1 de kernelSi uno se bloquea, se bloquea todo el proceso. No hay paralelismo real.
1×1 (one to one)Cada hilo de usuario → 1 de kernelMás concurrencia, pero el número de hilos de kernel es limitado.
M×N (many to many)Muchos de usuario → igual o menos de kernelLo mejor de ambos: hilos ilimitados y paralelismo; si uno se bloquea, el kernel planifica otro.

Estados de un hilo

TeoríaUT2.1

EstadoCuándo
NuevoCreado con new, aún sin start().
Listo / RunnableTras start(); puede estar ejecutándose o esperando CPU.
BloqueadoPor sleep(), esperando E/S, en wait() hasta un notify()/notifyAll(), en join(), o esperando un monitor synchronized.
TerminadoAcaba run() normalmente o por excepción / stop().
Un hilo terminado no se puede volver a arrancar. Llamar otra vez a start() lanza IllegalThreadStateException: hay que crear otro con new.

Crear hilos: Thread vs Runnable

TeoríaUT2.1

Lo que hace el hilo va siempre en run(). Se arranca con start(), que crea el hilo nuevo y llama a run(). Llamar a run() directamente ejecuta el código en el hilo actual, sin concurrencia.

// 1) Heredando de Thread
class MiHilo extends Thread {
    @Override
    public void run() { /* trabajo */ }
}
new MiHilo().start();

// 2) Implementando Runnable
class MiTarea implements Runnable {
    @Override
    public void run() { /* trabajo */ }
}
new Thread(new MiTarea()).start();

// 3) Lambda (Runnable es una interfaz funcional)
new Thread(() -> System.out.println("Hola desde " + Thread.currentThread().getName())).start();

implements Runnable

  • Más general: la clase puede heredar de otra clase.
  • Solo aporta run(); para el resto hay que usar Thread.currentThread().

extends Thread

  • Más sencillo: tienes a mano getName(), setPriority()...
  • Limitado: ya no puede heredar de otra clase (herencia simple).

Ejemplo Ratón: secuencial, hilos y join

TeoríaUT2.1 · 0_Ejemplo_Raton

Secuencial: cada ratón espera a que termine el anterior → tiempo total = suma (18 s). Con hilos todos empiezan a la vez → tiempo total ≈ el más lento (6 s).

// 0_Ejemplo_Raton: versión SECUENCIAL (sin hilos)
public class Raton {

    private String nombre;
    private int tiempoAlimentacion;   // segundos

    public Raton(String nombre, int tiempoAlimentacion) {
        this.nombre = nombre;
        this.tiempoAlimentacion = tiempoAlimentacion;
    }

    public void comer() {
        try {
            System.out.printf("El ratón %s ha comenzado a alimentarse%n", nombre);
            Thread.sleep(tiempoAlimentacion * 1000L);
            System.out.printf("El ratón %s ha terminado de alimentarse%n", nombre);
        } catch (InterruptedException e) {
            e.printStackTrace();
        }
    }

    public static void main(String[] args) {
        // Uno detrás de otro: tiempo total = 4+5+3+6 = 18 s
        new Raton("Fievel", 4).comer();
        new Raton("Jerry", 5).comer();
        new Raton("Pinky", 3).comer();
        new Raton("Mickey", 6).comer();
    }
}

public class RatonJoin {

    public static void main(String[] args) throws InterruptedException {
        Thread fievel = new Thread(new RatonRunnable("Fievel", 4));
        Thread jerry  = new Thread(new RatonRunnable("Jerry", 5));

Finalizar un hilo: isAlive e interrupt

TeoríaUT2.1B

  • La forma natural de morir es terminar run().
  • isAlive() dice si sigue vivo (desde start() hasta su muerte).
  • Para pararlo desde fuera: interrupt(). Si está en sleep/wait/join salta InterruptedException y en el catch programamos la salida (return).
  • return sale del hilo; System.exit(0) sale de todo el programa.
  • stop() está en desuso: no usar.
@Override
public void run() {
    try {
        while (!Thread.currentThread().isInterrupted()) {
            // trabajo
            Thread.sleep(500);
        }
    } catch (InterruptedException e) {
        // nos han interrumpido mientras dormíamos
    }
    System.out.println("Hilo terminado limpiamente");
}

ExecutorService y pool de hilos

TeoríaUT2.1B

Un pool de hilos es un contenedor con un número limitado de hilos que ejecutan todas las tareas de una cola. Evita crear tantos hilos que se agoten los recursos. Java recomienda usar ExecutorService en lugar de crear hilos a mano.

Executors.Crea
newFixedThreadPool(n)Pool de n hilos reutilizados cíclicamente.
newCachedThreadPool()Crea hilos según hace falta y reutiliza los libres; mata los inactivos.
newSingleThreadExecutor()Un solo hilo; si una tarea lanza excepción, las siguientes siguen.
newScheduledThreadPool(n)Tareas programadas (una vez o repetidas), como un Timer con varios hilos.
MétodoQué hace
execute(Runnable)De Executor. Ejecuta y nunca devuelve resultado.
submit(Runnable / Callable)De ExecutorService. Devuelve un Future (con Callable, el resultado).
shutdown()No acepta más tareas (submit lanza excepción) y deja terminar las que hay.
shutdownNow()Intenta parar todo: interrumpe los hilos.
isTerminated()true cuando, tras shutdown, ya no queda ninguna tarea.
awaitTermination(t, unidad)Bloquea hasta que termine todo: un join() masivo.

Ventajas

  • Desacopla qué se hace de cómo se ejecuta.
  • Reutiliza hilos: al acabar una tarea el hilo vuelve al pool → menos overhead.
  • Limita el número de hilos.
  • Permite recuperar resultados con Callable + Future.
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

// UT3_7_PoolHilos: 10 tareas repartidas entre solo 3 hilos reutilizados
public class PoolHilos {

    public static void main(String[] args) throws InterruptedException {
        ExecutorService pool = Executors.newFixedThreadPool(3);

        for (int i = 1; i <= 10; i++) {
            final int tarea = i;                    // las lambdas solo ven variables "final"
            pool.submit(() -> {
                System.out.println("Tarea " + tarea + " en " + Thread.currentThread().getName());
                try {
                    Thread.sleep(500);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            });
        }

        pool.shutdown();                            // no acepta más tareas; deja terminar las que hay
        pool.awaitTermination(1, TimeUnit.MINUTES); // como un join() de todas las tareas
        System.out.println("¿Terminado? " + pool.isTerminated());
    }
}
import java.util.concurrent.ExecutorService;

Problemas de concurrencia y sección crítica

TeoríaUT2.2

Los problemas aparecen cuando varios hilos acceden a un recurso compartido y limitado. No siempre provocan el mismo error, ni en todas las ejecuciones. Se resuelven haciendo secuenciales ciertas partes; si te pasas, todo el programa se vuelve secuencial y pierdes la concurrencia.

ProblemaQué es
Condición de carreraEl resultado depende del orden de acceso a memoria (c++ no es atómico).
Inconsistencia de memoriaHilos con visiones distintas del mismo dato (cachés de cada núcleo).
InaniciónUn hilo nunca consigue el recurso porque otros siempre entran antes.
InterbloqueoDos o más esperan para siempre un evento que solo puede producir otro bloqueado.
Bloqueo activo (livelock)Como el interbloqueo, pero los hilos cambian de estado continuamente sin avanzar.

Acción atómica y volatile

  • Atómica: sucede completa, sin interrupciones; su efecto solo se ve al final.
  • En Java son atómicas: leer/escribir primitivos excepto long y double, y leer/escribir variables volatile (incluidas long y double).
  • volatile hace que solo haya una copia de la variable visible para todos. Útil con un hilo que escribe y varios que leen. No arregla c++ con varios escritores.

Requisitos de una solución a la sección crítica

  1. Exclusión mutua: si uno está en su sección crítica, nadie más entra.
  2. Progreso: si nadie está dentro, solo los que quieren entrar deciden quién entra.
  3. Espera limitada: hay un límite de veces que otros pueden colarse.

Condiciones de la exclusión mutua (mutex)

  • Solo un proceso en la sección crítica de un recurso.
  • Ninguno que pida entrar puede ser postergado indefinidamente.
  • Si no hay nadie dentro, entra sin demora.
  • No se suponen velocidades ni número de procesadores.
  • Se permanece dentro un tiempo finito.

La sincronización se consigue por exclusión mutua (acceso exclusivo y finito) y por condición (no avanzar hasta que se cumpla algo). En Java ambas se basan en el monitor.

synchronized y monitores

TeoríaUT2.2

  • Limita un método o bloque a un único hilo a la vez → exclusión mutua.
  • El monitor es por instancia de objeto: todos los hilos que usan ese mismo objeto se excluyen entre sí. Con objetos distintos no hay exclusión.
  • Un método synchronized usa this como monitor: es equivalente a synchronized(this) { ... }.
  • Sincronizar demasiado código es poco eficiente: mejor solo la parte que toca la variable compartida.
  • Cada objeto tiene una cola de hilos esperando el bloqueo; el orden en que entran es indeterminista.
  • Al entrar en un bloque synchronized se actualizan las variables visibles; al salir, los cambios se escriben en memoria principal.
// Método sincronizado: monitor = this
public synchronized void incrementa() {
    c++;
}

// Bloque sincronizado: solo la parte crítica
public void add(int value) {
    // ... código no crítico ...
    synchronized (this) {
        this.count += value;
    }
}

// Con un objeto cerrojo propio (static si la variable es static)
private static final Object CERROJO = new Object();
synchronized (CERROJO) {
    contadorCompartido++;
}
Objeto monitor final: si reasignas el objeto usado como monitor se pierden los bloqueos. Decláralo final. Oracle recomienda no sincronizar sobre String ni wrappers (Integer, Boolean...). Lo seguro: this o un new Object().

Ejemplo: Sumador y Restador con un Contador compartido

Contador empieza en 100; un hilo suma 300 veces y otro resta 300 veces. Sin synchronized el resultado puede no ser 100. Lo importante: pasar el mismo objeto a los dos constructores.

// Objeto COMPARTIDO por los dos hilos (UT2_2_1_CompartirInfo2)
public class Contador {

    private int c;

    public Contador(int inicial) {
        this.c = inicial;
    }

    // c++ NO es atómico: leer c -> sumar 1 -> guardar c.
    // Sin synchronized dos hilos pueden intercalarse y perder operaciones (condición de carrera)
    public synchronized void incrementa() {
        c++;
    }

    public synchronized void decrementa() {
        c--;
    }

    public synchronized int valor() {
        return c;
    }
}
public class Sumador extends Thread {

    private Contador contador;

    public Sumador(String nombre, Contador contador) {
        super(nombre);                 // nombre del hilo
        this.contador = contador;
    }

    @Override
    public void run() {
        for (int i = 0; i < 300; i++) {
            contador.incrementa();
            try {
                Thread.sleep(10);
            } catch (InterruptedException e) {
                return;
            }
        }
        System.out.println(getName() + " termina. Valor: " + contador.valor());
    }
}
public class Restador extends Thread {

    private Contador contador;

    public Restador(String nombre, Contador contador) {
        super(nombre);
        this.contador = contador;
    }

    @Override

            contador.decrementa();
            try {
                Thread.sleep(10);
            } catch (InterruptedException e) {
                return;
            }

    public static void main(String[] args) throws InterruptedException {

// Ejercicio: 5 hilos incrementan 5000 veces una variable compartida
public class CincoHilos implements Runnable {

    private static int contador = 0;                    // compartida (static)
    private static final Object CERROJO = new Object(); // objeto monitor (final!)

    private boolean sincronizado;

    public CincoHilos(boolean sincronizado) {
        this.sincronizado = sincronizado;
    }

    @Override
    public void run() {
        for (int i = 0; i < 5000; i++) {
            if (sincronizado) {
                synchronized (CERROJO) {   // bloque sincronizado: solo 1 hilo a la vez
                    contador++;
                }
            } else {
                contador++;                // condición de carrera
            }
        }
    }

    private static int probar(boolean sync) throws InterruptedException {
        contador = 0;
        Thread[] hilos = new Thread[5];
        for (int i = 0; i < 5; i++) {
            hilos[i] = new Thread(new CincoHilos(sync));
            hilos[i].start();
        }
        for (Thread h : hilos) h.join();   // esperar a los 5
        return contador;
    }

    public static void main(String[] args) throws InterruptedException {
        System.out.println("Sin sincronizar: " + probar(false) + " (esperado 25000)");
        System.out.println("Sincronizado:    " + probar(true) + " (esperado 25000)");
    }
}

wait(), notify() y notifyAll()

TeoríaSincronización por condición · necesario para Aeropuerto y Dinamo

synchronized da exclusión mutua. Para esperar a que se cumpla una condición dentro de un monitor se usan los métodos de Object:

MétodoQué hace
wait()Suelta el monitor y duerme el hilo hasta que otro haga notify. Lanza InterruptedException.
notify()Despierta a un hilo cualquiera de los que esperan en ese monitor.
notifyAll()Despierta a todos; cada uno vuelve a comprobar su condición. El más seguro.
Reglas de oro: solo dentro de un método/bloque synchronized sobre ese objeto (si no, IllegalMonitorStateException), y la condición siempre en un while, nunca en un if.
public class Recurso {
    private boolean ocupado = false;

    public synchronized void entrar() throws InterruptedException {
        while (ocupado) {        // mientras NO pueda pasar...
            wait();              // ...espero
        }
        ocupado = true;          // paso
    }

    public synchronized void salir() {
        ocupado = false;
        notifyAll();             // aviso a los que esperan
    }
}

Productor–consumidor

import java.util.LinkedList;

// Monitor con sincronización por CONDICIÓN: wait() / notifyAll()
public class Buffer {

    private final LinkedList<Integer> cola = new LinkedList<>();
    private final int capacidad;

    public Buffer(int capacidad) {
        this.capacidad = capacidad;
    }

    public synchronized void poner(int dato) throws InterruptedException {
        while (cola.size() == capacidad) {   // SIEMPRE while, nunca if
            wait();                          // suelta el monitor y se duerme
        }
        cola.add(dato);
        System.out.println("Producido " + dato + "  -> buffer " + cola);
        notifyAll();                         // despierta a los que esperan
    }

    public synchronized int quitar() throws InterruptedException {
        while (cola.isEmpty()) {
            wait();
        }
        int dato = cola.removeFirst();
        System.out.println("Consumido " + dato + " <- buffer " + cola);
        notifyAll();
        return dato;
    }
}
public class ProductorConsumidor {

    public static void main(String[] args) {
        Buffer buffer = new Buffer(3);

        Thread productor = new Thread(() -> {
            try {
                for (int i = 1; i <= 10; i++) {
                    buffer.poner(i);
                    Thread.sleep(100);
                }
            } catch (InterruptedException e) { }
        });

        Thread consumidor = new Thread(() -> {
            try {
                for (int i = 1; i <= 10; i++) {
                    buffer.quitar();
                    Thread.sleep(300);       // más lento: el buffer se llena y el productor espera
                }
            } catch (InterruptedException e) { }
        });

        productor.start();
        consumidor.start();
    }
}

Prioridad de hilos

TeoríaUT2.2

ConstanteValor
Thread.MIN_PRIORITY1
Thread.NORM_PRIORITY5 (la del main)
Thread.MAX_PRIORITY10
  • Los hilos creados heredan la prioridad de su padre.
  • getPriority() / setPriority(n) (n entre 1 y 10).
  • Los 10 niveles de Java no coinciden con los del SO: usa solo las 3 constantes.
  • La prioridad es una sugerencia: los de mayor prioridad tienden a acabar antes, pero no está garantizado.
public class MemoriaComun {
    private int pasos = 0;
    // Método compartido y sincronizado por todos los hilos
    public synchronized void pasar() {
        pasos++;
    }
}
public class HiloPrioridad extends Thread {

    private MemoriaComun miMemoriaComun;

    public HiloPrioridad(int prioridad, MemoriaComun memoria) {
        this.miMemoriaComun = memoria;
        setPriority(prioridad);        // 1..10 (MIN_PRIORITY..MAX_PRIORITY)
    }

    // Ejecuta una tarea "pesada"
    @Override
    public void run() {
        for (int i = 0; i < 5000; ++i) {
            miMemoriaComun.pasar();
            Thread.yield();            // cede la CPU: el planificador elige otro hilo
        }
        System.out.println("Hilo de prioridad " + getPriority() + " termina ahora");
    }
}
public class ProgramaPrioridad {

    public static void main(String[] args) {
        int contador = 5;
        MemoriaComun memoria = new MemoriaComun();
        Thread[] hilosMIN = new Thread[contador];
        Thread[] hilosNORM = new Thread[contador];
        Thread[] hilosMAX = new Thread[contador];

        for (int i = 0; i < contador; i++) {
            hilosMIN[i] = new HiloPrioridad(Thread.MIN_PRIORITY, memoria);
            hilosNORM[i] = new HiloPrioridad(Thread.NORM_PRIORITY, memoria);
            hilosMAX[i] = new HiloPrioridad(Thread.MAX_PRIORITY, memoria);
        }
        System.out.println("Hilos en proceso, espera...\nLos de mayor prioridad TIENDEN a terminar antes...\n");

        for (int i = 0; i < contador; i++) {
            hilosMIN[i].start();
            hilosNORM[i].start();
            hilosMAX[i].start();
        }
        // La prioridad es una SUGERENCIA al SO: no garantiza el orden
    }
}

MultiHilo I · Ejercicio 5 · El artificiero y la bomba

Boletín resueltoisAlive + interrupt

Enunciado: una clase con 2 métodos: cuenta atrás de 9 a 0 (al llegar a 0 explota) y artificiero que tarda entre 9.500 y 10.500 ms en desactivarla. Se arranca uno u otro según un parámetro. Dos hilos; cuando uno acaba, se interrumpe el otro.
// Ejercicio 5 - El artificiero y la bomba  (extends Thread)
public class ArtificieroBomba extends Thread {

    private boolean esBomba;   // true = contador, false = artificiero

    public ArtificieroBomba(boolean esBomba) {
        this.esBomba = esBomba;
    }

    // Cuenta atrás 9..0 (1 s por número)
    public void contador() {
        try {
            for (int i = 9; i >= 0; i--) {
                System.out.println(i);
                Thread.sleep(1000);
            }
            System.out.println("PUUUUUUMMMMMMMMMM");
        } catch (InterruptedException e) {
            // Nos interrumpen = el artificiero la ha desactivado
            return;                 // return sale del hilo; System.exit(0) saldría del programa
        }
    }

    // Tarda entre 9500 y 10500 ms
    public void artificiero() {
        try {
            int ms = 9500 + (int) (Math.random() * 1001);
            System.out.println("El artificiero comienza a desactivar la bomba");
            Thread.sleep(ms);
            System.out.println("El artificiero ha desactivado la bomba");
        } catch (InterruptedException e) {
            return;                 // interrumpido = ha explotado
        }
    }

    @Override
    public void run() {
        if (esBomba) contador();
        else artificiero();
    }

    public static void main(String[] args) throws InterruptedException {
        ArtificieroBomba artificiero = new ArtificieroBomba(false);
        ArtificieroBomba bomba = new ArtificieroBomba(true);

        bomba.start();
        artificiero.start();

        // Esperamos mientras LOS DOS sigan vivos
        do {
            Thread.sleep(50);
        } while (bomba.isAlive() && artificiero.isAlive());

        if (bomba.isAlive()) {          // terminó antes el artificiero
            bomba.interrupt();
            System.out.println("La bomba ha sido desactivada");
        } else {                        // terminó antes la bomba
            artificiero.interrupt();
            System.out.println("El artificiero ha muerto");
        }

// MONITOR de la pista: solo un aeroplano a la vez y prioridad para los aviones
public class Pista {

    private boolean ocupada = false;
    private int avionesEsperando = 0;

    public synchronized void entrar(Aeroplano a) throws InterruptedException {
        if (a.esAvion()) avionesEsperando++;

        // Espera si la pista está ocupada,
        // o si es avioneta y hay algún avión esperando (prioridad)
        while (ocupada || (!a.esAvion() && avionesEsperando > 0)) {
            wait();
        }

        if (a.esAvion()) avionesEsperando--;
        ocupada = true;
        System.out.println("Aeroplano de tipo: " + a.getTipo() + " con número "
                + a.getName() + " entra en la pista de despegue...");
    }

    public synchronized void salir() {
        ocupada = false;
        notifyAll();      // despierta a todos; cada uno vuelve a comprobar su condición
    }
}

Enunciado (resumen): 400.000 soldados en la playa de Dunkerque. Se rescatan con lanchas (500–1.000 soldados/viaje) y botes salvavidas (1.500–2.000). En la playa solo puede haber lanchas o botes, nunca los dos; lo mismo al desembarcar en los barcos de alta mar. Embarcar dura media hora y desembarcar otra media. La operación acaba a los 6 días o cuando no queden soldados: los de la playa se rinden y los que van en lancha/bote llegan a Gran Bretaña. Información constante al alto mando. 1 h = 1000 ms.

Diseño: Operacion guarda los contadores (monitor). Zona es un monitor reutilizable para playa y alta mar que deja entrar a varios del mismo tipo pero nunca mezcla tipos (y cede el turno si el otro tipo espera, para evitar inanición). // Datos COMPARTIDOS de toda la operación (monitor)
public class Operacion {

    // 1 h = 1000 ms. Para probar rápido: java -Dhora=20 Dinamo
    public static final int HORA = Integer.getInteger("hora", 1000);
    public static final int DIAS = 6;

    private int enPlaya;
    private int rescatados = 0;          // llegados a los barcos de alta mar
    private int llegadosPorSuCuenta = 0; // iban en lancha/bote al acabar los 6 días
    private int enTransito = 0;          // a bordo de lanchas o botes ahora mismo
    private volatile boolean fin = false;

    public Operacion(int soldados) {
        this.enPlaya = soldados;
    }

    // Saca de la playa como mucho 'max' soldados
    public synchronized int embarcar(int max) {
        int n = Math.min(max, enPlaya);
        enPlaya -= n;
        enTransito += n;
        return n;
    }

    public synchronized void desembarcar(int n) {
        enTransito -= n;
        rescatados += n;
    }

    public synchronized void vuelvenPorSuCuenta(int n) {
        enTransito -= n;
        llegadosPorSuCuenta += n;
    }

    public synchronized int getEnPlaya()     { return enPlaya; }
    public synchronized int getRescatados()  { return rescatados; }
    public synchronized int getEnTransito()  { return enTransito; }
    public synchronized int getPorSuCuenta() { return llegadosPorSuCuenta; }

    public boolean isFin()   { return fin; }
    public void terminar()   { fin = true; }
}
// Monitor para la PLAYA y para el DESEMBARCO en alta mar:
// dentro solo puede haber lanchas o solo botes, nunca los dos tipos a la vez
public class Zona {

    private String nombre;
    private String tipoDentro = null;
    private int dentro = 0;
    private int esperandoLanchas = 0, esperandoBotes = 0;
    private boolean cerrada = false;

    public Zona(String nombre) {
        this.nombre = nombre;
    }

    private int esperandoOtro(String tipo) {
        return tipo.equals("LANCHA") ? esperandoBotes : esperandoLanchas;
    }

    // Devuelve false si la zona se ha cerrado (fin de la operación)
    public synchronized boolean entrar(String tipo) throws InterruptedException {
        if (tipo.equals("LANCHA")) esperandoLanchas++; else esperandoBotes++;

        // Puede entrar si está vacía, o si dentro hay de su tipo y el otro tipo no espera
        // (lo segundo evita que un tipo acapare la zona: INANICIÓN)
        while (!cerrada && !(dentro == 0
                || (tipo.equals(tipoDentro) && esperandoOtro(tipo) == 0))) {
            wait();
        }

        if (tipo.equals("LANCHA")) esperandoLanchas--; else esperandoBotes--;
        if (cerrada) return false;
        tipoDentro = tipo;
        dentro++;
        return true;
    }

    public synchronized void salir() {
        dentro--;
        if (dentro == 0) tipoDentro = null;
        notifyAll();
    }

    public synchronized void cerrar() {
        cerrada = true;
        notifyAll();      // despierta a los que esperaban para que terminen
    }
}

public class Embarcacion extends Thread {

    private String tipo;
    private int min, max;
    private Operacion op;
    private Zona playa, altaMar;
    private int viajes = 0, total = 0;

    public Embarcacion(String nombre, String tipo, int min, int max,
                       Operacion op, Zona playa, Zona altaMar) {
        super(nombre);
        this.tipo = tipo;
        this.min = min;
        this.max = max;
        this.op = op;
        this.playa = playa;
        this.altaMar = altaMar;
    }

    @Override
    public void run() {
        try {
            while (!op.isFin() && op.getEnPlaya() > 0) {
                // ---- 1. PLAYA ----
                if (!playa.entrar(tipo)) break;          // operación terminada
                int capacidad = min + (int) (Math.random() * (max - min + 1));
                int soldados = op.embarcar(capacidad);
                if (soldados == 0) {                     // ya no queda nadie
                    playa.salir();
                    break;
                }
                System.out.printf("  %s embarca %d soldados (quedan %d en la playa)%n",
                        getName(), soldados, op.getEnPlaya());
                Thread.sleep(Operacion.HORA / 2);        // embarcar: media hora
                playa.salir();

                // ---- 2. ALTA MAR ----
                if (op.isFin()) {                        // los barcos se han ido
                    op.vuelvenPorSuCuenta(soldados);
                    System.out.printf("  %s pone rumbo a Gran Bretaña con %d soldados%n", getName(), soldados);
                    break;
                }
                altaMar.entrar(tipo);
                Thread.sleep(Operacion.HORA / 2);        // desembarcar: media hora
                op.desembarcar(soldados);
                altaMar.salir();
                viajes++;
                total += soldados;
                System.out.printf("  %s deja %d soldados en los barcos%n", getName(), soldados);
            }
        } catch (InterruptedException e) {
            // no se usa: el fin se controla con op.isFin()
        }
    }

    public int getViajes() { return viajes; }
    public int getTotal()  { return total; }
}

// Monitor de la playa: máximo 7 grupos a la vez y prioridad para las BARCAS
public class Playa {

    private static final int MAX_GRUPOS = 7;
    private int dentro = 0;
    private int barcasEsperando = 0;
    private boolean cerrada = false;

    public synchronized boolean entrar(boolean esBarca) throws InterruptedException {
        if (esBarca) barcasEsperando++;

        while (!cerrada && (dentro >= MAX_GRUPOS || (!esBarca && barcasEsperando > 0))) {
            wait();
        }

        if (esBarca) barcasEsperando--;
        if (cerrada) return false;
        dentro++;
        return true;
    }

    public synchronized void salir() {
        dentro--;
        notifyAll();
    }

    public synchronized void cerrar() {
        cerrada = true;
        notifyAll();
    }
}
// Un grupo de barcas (botes salvavidas) o de lanchas
public class Grupo extends Thread {

        this.barca = barca;
        this.op = op;
        this.playa = playa;

            while (!op.isFin() && op.getEnPlaya() > 0) {
                if (!playa.entrar(barca)) break;

Repaso tipo test

TestPulsa cada pregunta para ver la respuesta

¿Diferencia entre programa y proceso?
El programa es estático (instrucciones en disco); el proceso es un programa en ejecución con su memoria, PID y estado.
¿Qué comparten los hilos de un proceso y qué tiene cada uno?
Comparten código, datos (static/globales) y ficheros. Cada uno tiene id, contador de programa, registros y pila.
¿Qué es un cambio de contexto y por qué es caro?
Guardar el estado de un proceso (en el PCB) y cargar el de otro. Durante ese tiempo la CPU no hace trabajo útil.
¿Dónde se guarda el contexto de un proceso?
En el PCB (Bloque de Control de Proceso).
Multitarea cooperativa vs preferente
Cooperativa: el proceso cede la CPU voluntariamente (Windows 3.11). Preferente: el SO reparte la CPU y expulsa procesos (UNIX, Windows NT).
¿Concurrente es lo mismo que paralelo?
No. Concurrente: varias tareas avanzan intercaladas (puede ser con 1 CPU). Paralelo: se ejecutan a la vez en varias CPU.
Tres características de un sistema distribuido
Concurrencia, inexistencia de reloj global y fallos independientes.
¿Qué devuelve getInputStream() de Process?
La salida estándar del hijo (lo que imprime), para que el padre la lea.
¿Qué valor indica que el hijo acabó bien?
0, por convenio.
¿Qué pasa si redirijo la entrada con redirectInput?
getOutputStream() devuelve un NullOutputStream: ya no se puede escribir al hijo.
¿Qué método bloquea al padre hasta que acabe el hijo?
waitFor().
¿Cuál es la forma recomendada de sincronizar procesos con ficheros en Java?
FileChannel.lock() (FileLock de Java NIO), con un fichero solo para el bloqueo.
¿Por qué while(lock.exists()) + createNewFile() no es correcto?
Dos procesos pueden pasar exists() a la vez y entrar los dos.
Semáforo binario vs general
Binario: 0 o 1. General: cualquier entero no negativo. 0 = cerrado, >0 = abierto.
Paso de mensajes síncrono vs asíncrono
Síncrono: el emisor espera a que se reciba (rendezvous, RPC). Asíncrono: no espera; usa buzones.
Interbloqueo vs inanición
Interbloqueo: varios esperan para siempre recursos que tienen otros del grupo. Inanición: uno nunca consigue el recurso porque otros entran antes.
¿Diferencia entre start() y run()?
start() crea un hilo nuevo que ejecuta run(). Llamar a run() lo ejecuta en el hilo actual, sin concurrencia.
¿Cuándo usar Runnable en vez de extends Thread?
Cuando la clase ya hereda de otra (Java solo tiene herencia simple).
¿Qué hace join()?
El hilo que llama espera a que termine el hilo sobre el que se invoca.
¿Cómo se para un hilo de forma segura?
Con interrupt() (salta InterruptedException en sleep/wait) o una bandera volatile. stop() está deprecado.
¿Qué operaciones son atómicas en Java?
Leer/escribir primitivos salvo long y double, y cualquier variable volatile.
¿Sobre qué objeto sincroniza un método synchronized?
Sobre this (la instancia). Es equivalente a synchronized(this){...}.
¿Sobre qué objetos NO se recomienda sincronizar?
String y wrappers (Integer, Boolean...). Usa this o un final Object.
Requisitos de una solución a la sección crítica
Exclusión mutua, progreso y espera limitada.
Prioridad por defecto del main y rango
5 (NORM_PRIORITY). Rango 1 (MIN) a 10 (MAX). Es solo una sugerencia.
shutdown() vs shutdownNow()
shutdown: no acepta tareas nuevas y deja terminar las actuales. shutdownNow: intenta parar todas interrumpiendo los hilos.
execute() vs submit()
execute (Executor) no devuelve nada. submit (ExecutorService) devuelve un Future; con Callable, el resultado.
¿Por qué wait() siempre dentro de un while?
Porque al despertar la condición puede no cumplirse (otro hilo entró antes, o despertar espurio).
Modelo de hilos M×N
Muchos hilos de usuario sobre igual o menos hilos de kernel: hilos ilimitados, paralelismo y, si uno se bloquea, el kernel planifica otro.
